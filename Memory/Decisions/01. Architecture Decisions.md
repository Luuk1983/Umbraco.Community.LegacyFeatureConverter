# Architectural Decisions Record

## ADR-001: Multi-project structure with single NuGet package
**Decision:** Split into Abstractions, Data, Infrastructure, Converters as separate class libraries, all referenced by the main Razor SDK plugin project which produces the NuGet package.
**Rationale:** Separation of concerns, testability, and keeps each project small and focused. Standard ProjectReferences include DLLs automatically in the package.

## ADR-001a: Dedicated Data project for database concerns
**Decision:** EF Core DbContext, entities, migrations, and provider detection live in their own `LP.Umbraco.LegacyFeatureConverter.Data` project, separate from Infrastructure.
**Rationale:** Database concerns (schema, migrations, provider config) are distinct from the services that use them. Keeps both projects smaller and more focused. Infrastructure depends on Data, not vice versa.

## ADR-001b: ".Abstractions" naming over ".Core"
**Decision:** Name the interfaces/models project `LP.Umbraco.LegacyFeatureConverter.Abstractions` instead of `.Core`.
**Rationale:** `.Abstractions` is the idiomatic .NET convention (e.g., `Microsoft.Extensions.Logging.Abstractions`) for projects containing only interfaces, base classes, models, and enums — no concrete implementation. This signals clearly to package consumers that they can reference just this project to build their own converters without pulling in EF Core or other implementation dependencies.

## ADR-002: Entity Framework Core for all database access
**Decision:** Use EF Core exclusively for database operations (history, logs, queue). Multi-DB support via provider-specific DbContext subclasses (SQL Server + SQLite).
**Rationale:** Umbraco 13 natively supports EF Core via `AddUmbracoDbContext`. Database-agnostic, migrations are handled cleanly, and it's the standard for modern .NET data access.

## ADR-003: Template Method pattern for converters
**Decision:** `BasePropertyConverter` implements a fixed 4-phase workflow. Derived converters only implement `CreateTargetDataTypeAsync` and `ConvertPropertyValueAsync`.
**Rationale:** Proven in the reference project. Reduces duplication across converters while maintaining consistent execution (scanning, data type creation, doc type updates, content conversion).

## ADR-004: DI-based converter discovery (not reflection)
**Decision:** Converters are registered as `IPropertyConverter` in DI. `IConverterService` receives them via `IEnumerable<IPropertyConverter>`.
**Rationale:** Cleaner than raw reflection, leverages Umbraco's existing DI infrastructure, easily extensible by package consumers (just register their converter in a Composer).

## ADR-005: Database-backed queue with background task
**Decision:** Conversions are queued to a database table and processed by a background `IHostedService`, not executed synchronously in HTTP requests.
**Rationale:** Prevents HTTP timeouts for long conversions, survives application restarts (unlike in-memory queues), enables real-time progress via SignalR.

## ADR-006: Scope-per-save pattern
**Decision:** Every `Save()` call (data type, document type, content) gets its own `IScopeProvider.CreateScope()` block.
**Rationale:** Prevents database lock timeouts, especially with SQLite. Proven necessary in the reference project. For test runs, the scope is created but `Complete()` is not called, causing an automatic rollback.

## ADR-007: MSTest for testing
**Decision:** Use MSTest + Moq + in-memory SQLite.
**Rationale:** User preference. MSTest is well-supported and straightforward.

## ADR-008: Notification suppression during conversions
**Decision:** Suppress Umbraco notifications (cache invalidation, indexing, etc.) during bulk conversion saves. Trigger a single refresh after completion.
**Rationale:** Performance — without suppression, each save triggers notification handlers (cache updates, uSync handlers, Examine indexing). Inspired by uSync's approach.

## ADR-009: Namespace: LP.Umbraco.LegacyFeatureConverter
**Decision:** Use `LP.Umbraco.LegacyFeatureConverter` namespace (matching the existing project), not the old project's `Umbraco.Community.LegacyFeatureConverter`.
**Rationale:** Consistent with the existing project setup and NuGet package ID.
