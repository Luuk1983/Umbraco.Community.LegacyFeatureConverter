# Legacy property editor conversion

## Functional description
I want to create an Umbraco 13 plugin that can convert Data Types and content based on legacy property editors to a new property editor. 
For the first version I want to be able to do these conversions:

- Nested Content > Block list
- Legacy image picker(s) > Image Picker 3

In the future I want to also use this to upgrade macro's, but that out of the scope of the session. 

In the backoffice of Umbraco, I want to add a new menu section in the menu of the settings section of Umbraco. This heading should be called 'Legacy converters'. In that menu section I want a menu called 'Property editors'. In another session we can also add the a menu item for macro's here.

When an editor opens the 'Property editors' menu, it should display a list of completed, in progress or waiting conversions. For running conversions I want to see the progress and this progress should update automatically. 

YOu can view the details of any conersion. Logging is a very important because if a conversion fails, the editor should get as much information as possible where it went wrong and why, so that he may fix it.

The screen should also provide the option to start a new conversion. This should display a list of all possible conversions to choose from. As mentioned before, we want to ship with Nested content and legacy media picker. The editor can then pick one of the conversions to start a wizard.

Step one should display a welcome and an introduction what the converter is used for.

Step 2 is an overview of all document types that have or had nested content, the properties that are or were nested content and how many pages will be updated. The editor can then select the document types that the editor want to update.

It's very important to understand that if uSync is used and the conversion ran on a development environment and was then deployed to other environments, like test and acceptance, that uSync will already update the document types to use the new format. The content still needs to be updated though.

THe last step is for setting a few settings:
- What to do when a conversion fails: stop or continue with the next
- Run a test run before the actual conversion. This takes longer, but a test run should do as much as possible as the actual conversion run, but whithout making any changes to the data. This will hopefully catch any errors before starting the migration.

The editor can now queue the migration.

## Development
For development I want you to take the following into consideration:

- When doing research, but absolutely sure you are researching for UMbraco 13 and NOT for newer versions! The source code for Umbraco is on Github and the v13 branch is v13/main.
- I want test driven development; write the tests first, then the actual code.
- This is going to be a public package that is going to be maintained for a long time. I want high quality code that's maintainable.
- I want a clear seperation of concerns. Distinct functionality (for instance, database handling) should have it's own project to keep the projects small and testable. IN the end I only want ONE package, so these multiple dlls should all be combined when building a NuGet package.
- I want consumer of this package to be able to easily extend it with it's own conversions. So I want a conversion (for instance nested content > block list) to be abstracted well with it's own interface. I also want to use reflection to get all conversions in a solution. This way, consumers can easily add their own like in a plugin system.
- All texts that are displayed in the Umbraco interface should be localized. I want to support English and Dutch by default.
- Even though Umbraco 13 still used AngularJS, it does ship by default with the Umbraco UUI Library that you can use without any additional installation. Use as much UUI components as possible. AngularJs doesn't always play nice with web components, but most components are prety useful.
- Performance essential! I want to be absolutely sure that we're not having issues with Umbraco scoping, threads or database connection pools. Especially database locking can be an issue if too many Umbraco saves are fired in rapid succession. That's why I want to use a background job and a queue system. This queue system should survive a restart of the application.
- Consider supressing notifications during a conversion. This should perform better because it skips a lot of notification handling, like updating cache. uSync does this as well. Maybe you can draw inspiration from that. Their source is also on github.
- Everything should be XML documented, even all private methods.
