This plan is for a first revision of the functionality that was created in a previous plan. adrs and the previous plan can be found in the /memory folder of the project.
The following things should be changed or fixed:

- Localization of setting menu item shows legacyConverter_treeTitle, so that localization does not work correctly.
- The calculation of how many document types are affected by an upgrade should be calculated up front. One of the last remarks of a previous setting was this:
"BasePropertyConverter (ConvertContentDataAsync): Added a Phase 4b second scan that iterates all doc types using the TargetPropertyEditorAlias, skipping those already handled in Phase 1. For each property, it calls ConvertPropertyValueAsync which acts as the gate — returns null if already in target format (NestedContent converter: can't parse BlockList JSON as JArray → null; MediaPicker converter: detects [ prefix → null), converts and saves only when the value is genuinely in old format."

I don't agree with this. I want the full calculation be done upfront. SO I want to check what document types need updating because they use nested content, but I also want to check from the perspective of content. The reason is that if you use uSync, it's possible that the document types are already updated by usync, but the content is not. So only scanning from the perspective of the document types is not enough because if uSync already updated the document types there is no way to tell what was nested content anymore. Because this is probably a heavy operation that takes some time, I think we should not show the number of impacted property types until the user hits the step in the wizard where he or she need to select the document types to update. For now, I don't want them to select individual pages, so I ony want to show the impacted document types and the number of pages and properties impacted. If the document type itself is already updated, it should somehow convey the message that it's only a data migration and that the document type is already updated correctly. 

- On the conversion dashboard, the 'available converters' are shown as some sort of card. I want these cards to be more compact and better looking. I want them to have an icon and a title and something more obvious in the design that tells the editor that you can click it to start a conversion. So the description can go away because the first page of the wizard is for a description. Use Umbraco UI library components if possible. Also, the card shows the number of impacted document types. However, like I mentioned in the previous item, I don't think we should.
- When you go into the details of a conversion history item, you cannot navigate back, except by using the back button of the browser. This should be improved.
- There is too little use of uui-components, especially for tables. But also uui-box. See the umbraco-ui repository on github or uui.umbraco.com for a gitbook. I want to make much more use of the uui components where possible. You looked a bit too much in the reference project I gave you for the design, because the design is a bit of a mess. Using uui-components hopefully fixes this.
- Too much logging, logging history of a single run with 1000's of nodes would get way too long. I think we need less verbose logging. So one log entry for a data editor that gets updated and one log entry per page that gets updated maybe? Ofcourse errors and warnings should be logged in as much detail as possible.
- On the Legacy Feature Converter dashboard, there is a 'enter description' textbox in the header. This is what you usually see when you edit a document type. This is probably due to reusing Umbraco components wrong.
- When is the conversion queue cleared? I would think that if something is completed, it should be removed from the queue because then it would be available in the history. When a conversion is done and shown as 'completed', the history table does not automatically update.
- I want to add an additional option for the editor in the wizard to only save the changes, but not publish them.
- A conversion on nested content to block list where the node and the nested content vary by culture doesn't seem to go well.

Once again, I want a test-first approach. Write or update unit tests first, then write the code and verify against the test. I want you to be absolutely sure about everything you do. If you are not 100% confident, research further or ask me for clarification.
